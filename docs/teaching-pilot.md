# Try the lessons with beginners

This is a plan for an observation session, not a claim that a classroom trial
has happened. Use the local preview so setup problems do not hide language problems.

Invite three to five people who have not programmed before. Let each choose one
language. Start at 25 lights and keep the same language for the session. Explain
that we are testing the lessons, not the person. Ask them to say what they expect
before pressing Start. Avoid correcting a prediction until they have tried it.

## Session one: instructions, names and loops

Allow about 45 minutes, with breaks whenever helpful.

1. Open lesson 1. Ask: “Which light is first? Which is last? What happens if both
   instructions paint the same light?” Let them change a colour.
2. Open lesson 2. Ask them to change both end lights by changing one named value.
   Ask what the name holds just before each drawing instruction.
3. Open lesson 3. Ask for a prediction with five lights, then try 25. Ask them to
   make stripes. Can they describe what repeats without using a technical term?
4. Open lesson 3's mistake. Let them follow the error location and repair it.
   Record whether the message explains the problem without teacher translation.
5. Save locally, choose another lesson and import the saved file. Ask them to
   explain which changes were kept.

## Session two: time, memory and functions

Use lessons 5, 6 and 7 after choices are understood. Ask what happens during a
zero-second frame and a one-second frame. Let them reverse a moving dot and add
a second marker using the drawing function. Ask them to identify a value that
starts fresh on each call and one that is remembered. Ask why a loop that paints
25 positions does not create 25 visible animation frames.

Try the endless-loop mistake. Can they stop, locate and repair it? Use stepping
only when they need to inspect a value; do not make the debugger an extra subject
before it solves an obvious problem.

## Record observations

For each task, record:

| Item | Observation |
| --- | --- |
| Language, strip/ring and count | |
| Prediction before running | |
| What they changed and why | |
| Result they noticed | |
| Exact confusing word or message | |
| Help given, including a direct answer | |
| Could they explain the repair afterward? | |
| Could they make a different working change alone? | |
| Time to first successful change and time stuck | |

Use three simple outcome labels: **did it alone**, **did it after a hint**, and
**needed the answer**. Do not turn speed into a learner grade. A successful pilot
means people can predict a short loop, explain an exclusive endpoint, distinguish
one frame from movement over time, and make a new change without copying it.

Revise repeated points of confusion before claiming the course is ready for a
class. Repeat the task with a fresh beginner after a wording or interface change.
Keep actual observations separate from automated test results. Nothing in the
current acceptance report establishes beginner comprehension.
