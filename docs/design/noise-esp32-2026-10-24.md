# ESP32 noise measurements — 24 October 2026

Historical build labels and feature floors in this record predate the
[0.1.0 milestone baseline](../versioning.md). They describe the recorded
experiments and do not define current compatibility requirements.

All three boards completed 24 animated timing windows, 24 live-input windows and
192 exact RGB comparisons each. All **576 RGB comparisons passed**. There were no
in-window reboots or thermal stops. Inputs were accepted near 10 Hz, but heavy
noise scenes can render substantially slower and exhibit long input-to-frame
delays. In particular, prepared 1,024-pixel 3D scenes on C3 completed about
2.65 updates/s, with full-RGB readback delays reaching 1.68 s under repeated
snapshot polling. Correctness does not imply a low-latency control loop.

These are **short hardware screens**, not a five-pair optimisation acceptance or
endurance result. One three-second window per function/mode/count was used, with
one second of warmup; no long-run stability claim is made. The user requested
avoiding an hour-long wait. These measurements are a separate cohort from the
[ESP32 board optimisation campaign](esp32-optimisation-2026-10-24.md).

## Conditions and definitions

- Core 1.4.0 at frozen source `7b03d8978b82a6d01d73ab7ef827f2467966b389`: noise
  `8332324` merged with board firmware `e3c3dd3`. The later board report commit
  `67b0675` changes no ESP32 firmware sources.
- ESP-IDF 5.5.3, GCC 14.2.0, AUTO profiles, 160 MHz CPU on all three boards;
  one actual render worker, 2,000 µs render slice/epoch, 256-byte bytecode cache,
  128 KiB VM heap and 16 KiB main-task stack reservation. Float contraction off.
- Full Wi-Fi/HTTP/WebSocket/MQTT/boot build, unprovisioned AP, no intentional network
  or broker traffic. USB STATUS at 20 Hz, native temperature checks every two
  seconds on the same Client; stop at 80 °C or invalid/stale temperature.
- WS2812B/RMT output, GRB, brightness limit 32. C3 pin D1; C6/S3 D0. Counts are
  logical: physical strip length/wiring and optical output are unverified. Boards
  ran concurrently on the same USB host; this is not an isolated CPU comparison.
- One noise sample per pixel plus coordinate, VM and grayscale RGB work. Animated
  timing uses a 30-second ping-pong phase Ramp. Scalar and prepared packages come
  from the same source; frozen bytecode and host RGB hashes are archived.
- Live windows publish scale/phase/field at 10 Hz. Field is a latched seed count,
  not an event queue. Settled replays cover independent phase/scale changes,
  repeated/skipped counts, the seed sign bit and restoring the original field.
- Pixel loops and prepared maps currently report `render_reusable=false`: the
  runtime reuse proof covers straight-line expressions only. Completed renders
  can exceed input publications, or fall behind them; intermediate published
  values need not each produce a frame.

## Live input and output latency

Live publishers sustained the rates below. Acceptance p95 is the worst p95 among
the 24 short windows, not a pooled long-run percentile. Command acknowledgement
does not mean the corresponding pixels have reached the output.

| Metric | C3 | C6 | S3 |
| --- | ---: | ---: | ---: |
| Actual publications/s | 9.96–9.98 | 9.98–9.99 | 9.97–9.99 |
| Worst-window input acceptance p95 (ms) | 10.50 | 8.17 | 11.30 |
| Worst-window live STATUS p95 (ms) | 9.19 | 7.59 | 9.91 |

The following prepared-mode rows pool 32 settled changes per board/count (eight
states for each of four functions, including repeated values). Each cell is
**median / maximum host input-to-composite-readback milliseconds**. The probe
repeatedly requests full RGB snapshots until the exact expected frame appears;
USB transfer, polling and observer load are included. This is not optical timing.
The separate firmware `dirty_to_display_us` samples are retained in the JSON;
no-change events are excluded from that summary, and its clock boundary differs.

| Logical pixels | C3 | C6 | S3 |
| --- | ---: | ---: | ---: |
| 200 | 149.3 / 231.2 | 74.3 / 119.8 | 76.0 / 108.6 |
| 500 | 370.9 / 658.2 | 203.9 / 360.3 | 165.7 / 321.1 |
| 1,024 | 1097.8 / 1680.4 | 434.6 / 719.6 | 423.9 / 749.5 |

At 200 pixels, S3 has the lowest prepared render cost for all four functions.
C6 completes more updates/s for perlin2, simplex2 and simplex3; S3 leads perlin3.
Render CPU time alone does not determine output cadence. At 1,024 pixels, C3
3D render rates are well below the 10 Hz input rate: producers should use latest
values/latched counts and must not assume every intermediate value is rendered.
The latency measurements identify an optimisation target; they do not establish
a universal control-response bound.

existing 2 MiB application partitions.

## Verification, cleanup and evidence

- Bootloader, partition table and application writes were followed by explicit
  `verify_flash` on every board. Package readback matched the frozen hashes.
- Every timing/live/replay group completed; generations remained stable and
  boot IDs were unchanged throughout each board’s measurement run.
- Afterward, each board was reset and checked: core 1.4.0, empty active/saved
  output configuration, no programs/presets and no temporary `noise.*` sources.
  All serial clients are closed and all three ports were released.
- The merged host passed 24 CTest suites, 44 focused Python tests and 192 frozen
  RGB replays before hardware measurement. Earlier host/WASM/sanitizer/core
  checks are recorded in [the noise contract](../noise.md).
